# Database

Elektra is primarily an OpenStack dashboard — the vast majority of data lives in
OpenStack APIs. The local PostgreSQL database stores only what OpenStack cannot:
URL slug mappings, an API-response cache, user profile metadata, and the inquiry
workflow data.

Single database, single schema (`db/schema.rb`). No multi-db setup.

```
Connection: PostgreSQL via env vars
  MONSOON_DB_USER / MONSOON_DB_PASSWORD
  ELEKTRA_POSTGRESQL_SERVICE_HOST / POSTGRES_SERVICE_HOST (multiple fallbacks)
  ELEKTRA_POSTGRESQL_SERVICE_PORT / POSTGRES_SERVICE_PORT
  MONSOON_DB_NAME (default: monsoon-dashboard_development / _production)
```

## Tables at a glance

| Table | AR Model | Purpose |
|-------|----------|---------|
| `friendly_id_entries` | `FriendlyIdEntry` | UUID ↔ human-readable slug mapping for domains and projects |
| `object_cache` | `ObjectCache` | Denormalized cache of OpenStack API responses — populated by Elektron middleware on every request |
| `user_profiles` | `UserProfile` | Local copy of user display name / email (OpenStack identity doesn't expose these on every token) |
| `domain_profiles` | `DomainProfile` | Per-domain ToU acceptance records; FK to `user_profiles` |
| `project_profiles` | `ProjectProfile` | Per-project wizard completion state (YAML blob) |
| `inquiry_inquiries` | `Inquiry::Inquiry` | Full inquiry/request objects with AASM state machine |
| `inquiry_process_steps` | `Inquiry::ProcessStep` | Audit trail of state transitions per inquiry |
| `inquiry_processors` | `Inquiry::Processor` | Users who can process/approve inquiries (cached from identity) |
| `inquiry_inquiries_processors` | (join table) | M:N between inquiries and processors |

## Table details

### `friendly_id_entries`

Maps OpenStack UUIDs to human-readable slugs used in Elektra's URLs
(`/ccadmin/cloud_admin/` instead of `/abc123/def456/`).

**Columns:** `class_name` (`"Domain"` / `"Project"`), `key` (UUID), `slug`
(human-readable, generated by `friendly_id` gem), `name` (display name),
`scope` (domain UUID for projects, null for domains), `endpoint` (Keystone URL —
disambiguates entries across environments).

### Lifecycle — how entries are created

Every request to a scoped URL passes through `ScopeController#load_scoped_objects`
(prepend_before_action). It calls `Dashboard::RescopingService.new(service_user)`,
then:

1. `rescoping_service.domain_friendly_id(key_or_slug)` — ILIKE match on both `key`
   and `slug` columns, filtered by current `endpoint`.
2. **Cache miss** → `service_user.identity.find_domain(id)` (Keystone API call).
3. Entry found in Keystone → `FriendlyIdEntry.find_or_create_entry("Domain", nil, domain.id, domain.name)`.
   The `friendly_id` gem auto-generates `slug` from `name`.
4. Same flow for project: `find_or_create_entry("Project", project.domain_id, project.id, project.name)` —
   `scope` = domain UUID (needed because project names are not globally unique; the
   `friendly_id` `:scoped` strategy partitions slug uniqueness per domain).

**Endpoint mismatch edge case:** if entries exist but `endpoint !=
Rails.application.config.keystone_endpoint`, `find_or_create_entry` calls
`entries.delete_all` and recreates. Handles DB migrations between environments.

### UUID → slug redirect

If the URL contains a raw UUID where a slug is expected (`domain_id !=
@scoped_domain_fid`), `load_scoped_objects` does a `gsub` on `request.path`
replacing the UUID with the slug and redirects. UUID bookmarks auto-redirect
transparently.

### Rename and delete

- **Rename:** `FriendlyIdEntry.update_project_entry(project)` sets `slug = nil` then
  saves — `friendly_id` regenerates the slug from the new name. Name unchanged → entry
  left alone.
- **Delete:** `FriendlyIdEntry.delete_project_entry(project)` removes the entry.
  Deletions performed directly in OpenStack (bypassing Elektra) leave orphan entries.

### Path generation

`plugin("compute").service_path(...)` builds URLs using `@scoped_domain_fid` and
`@scoped_project_fid` (the slug values). Generated links always use slug form.

**Key methods:**
- `FriendlyIdEntry.find_domain(key_or_slug)` — looks up by UUID or slug
- `FriendlyIdEntry.find_project(domain_id, key_or_slug)` — scoped to domain
- `FriendlyIdEntry.find_or_create_entry(class_name, scope, key, name)` — upserts; handles endpoint mismatch
- `FriendlyIdEntry.update_project_entry(project)` — called when project is renamed
- `FriendlyIdEntry.search(class_name, scope, term)` — ILIKE on `key` + `name`;
  used by the lookup plugin and by `ObjectCache.find_objects` to resolve friendly
  names to UUIDs

**Populated by:** `RescopingService` on every scoped request (cache miss → Keystone call).
**Used by:** `ScopeController#load_scoped_objects`, `ObjectCache.find_objects`, `lookup` plugin.

### `object_cache`

Denormalized cache of OpenStack objects. Every successful API response
processed by Elektron's `ObjectCache` middleware
(`lib/core/elektron_middlewares/object_cache.rb`) is stored here.

**Columns:** `id` (string — OpenStack object UUID or composite key), `cached_object_type`
(e.g. `"server"`, `"network"`), `name`, `project_id`, `domain_id`,
`search_label` (concatenated searchable fields), `payload` (JSON — full
response hash, merged across calls).

### Write path — the middleware

`Core::ElektronMiddlewares::ObjectCache#call` runs on every Elektron response:

**Error path (HTTP >= 400):** creates an `error`-type object. ID = request's `req-*`
header (OpenStack request-tracing convention) or `SecureRandom.hex`. Payload = response
body + service_name, http_method, path, project_id from request context.

**Success path:** calls `find_objects(response.body)` — a recursive walk:

```
Hash with id key + >1 keys  → cache it; type = parent_key.singularize
Hash with only id key        → skip (stub reference, not worth caching)
Hash without id key          → recurse into values
Array                        → recurse each element
parent_key in blacklist      → skip (e.g. "versions", "version")
```

`parent_key.singularize` derives the type from context: `{ "servers": [{...}] }` →
`cached_object_type = "server"`. **Aggregate special case:** ID becomes
`"aggregate_#{data["id"]}"` to avoid collision with flavor IDs.

**Role assignments:** have no native `id` field. The middleware parses the
`links.assignment` URL to extract entity IDs (project, user, role, group, domain)
and joins them as a composite key (`project_id-user_id-role_id`). Type is also
URL-derived (`project_user_role_assignment` etc.).

### Payload merging

`cache_objects` loads existing payloads, deep-merges new data on top, then bulk
updates and inserts. Fields accumulate over time — a richer `show` response
preserves its extra fields even when a later `list` response for the same object
omits them.

### `search_label`

`TYPE_SEARCH_LABEL_KEYS` maps each type to payload fields that should be
full-text indexed. For `"server"`: `description hostId user_id addresses
OS-EXT-SRV-ATTR:host`. These are concatenated as `"key: value key: value"` into
the `search_label` column. Types not in the map are searchable only by
`id`, `name`, `project_id`, `domain_id`.

### Consumer: `lookup` plugin

`ObjectCache.find_objects(type:, term:, include_scope:)`:

1. Queries `FriendlyIdEntry` to find UUIDs matching `term` by name/slug.
2. ORs `where(id: friendly_uuid_ids).or(search_label/name/id ILIKE term)`.

Searching `"marioworld"` finds all objects scoped to that project even when
searching by project name rather than UUID. `include_scope: true` → `includes(:domain, project: :domain)`
enriches each result with human-readable scope names for display.

### Consumer: `cloudops` topology

`Cloudops::TopologyObjectsController` queries the cache directly — zero live API calls:

```ruby
object = ObjectCache.where(id: params[:topology_object_id]).first
children = ObjectCache.where.not(cached_object_type: %w[error message])
  .where("project_id ILIKE :t OR domain_id ILIKE :t OR search_label ILIKE :t",
         t: "%#{object.id}%")
```

Finds all objects referencing the given object's ID anywhere in their scope or
`search_label`. This is how the topology graph is built.

**Important:** this cache is never explicitly expired. It grows unboundedly. Deleted
OS objects remain until manually purged. There is no TTL, no expiry job, no purge
on delete (only `delete_project_entry` when Elektra itself deletes a project).

### `user_profiles`

Local copy of user display name and email. OpenStack Keystone tokens do not carry
`email` or `full_name` — these are only available via a separate `find_user` API call.

**Columns:** `uid` (Keystone user UUID), `name` (username), `full_name`, `email`.

**Populated by:** `CurrentUserWrapper` on first login for the current user
(`app/controllers/concerns/current_user_wrapper.rb`): calls
`service_user.identity.find_user(current_user.id)` and saves the result via
`UserProfile.find_by_name_or_create_or_update`.

Also by `Inquiry::Processor.from_users` when creating/updating processors.

**Used for:** ToU acceptance check (`UserProfile.tou_accepted?`), user lookup
by name in the UI (role assignment dialog), processor name display in inquiry.

**Caveat (from code comment):** since Keystone user IDs are per-domain, a natural
user who logs into multiple domains will accumulate one `UserProfile` per domain.
There is no deduplication across domains.

---

### `domain_profiles`

Records that a user has accepted the Terms of Use for a specific domain.

**Columns:** `user_profile_id` (FK), `domain_id`, `tou_version`.

**Usage:** `UserProfile.tou_accepted?(user_id, domain_id, version)` — used in
`DashboardController` to gate access until ToU is accepted.

---

### `project_profiles`

Per-project wizard completion tracking. When a new project is created in Elektra,
a setup wizard guides the user through enabling services (networking, compute, etc.).
`ProjectProfile` stores which wizard steps are done, skipped, or pending.

**Columns:** `project_id` (OpenStack project UUID), `wizard_payload` (YAML blob).

**Payload structure:**
```ruby
{
  "networking" => { "status" => "done",    "data" => { ... } },
  "compute"    => { "status" => "skipped", "data" => nil },
  "dns"        => { "status" => "pending", "data" => nil }
}
```

**Key methods:** `wizard_finished?(*service_names)`, `wizard_skipped?(name)`,
`update_wizard_status(name, status, data)`.

### `inquiry_inquiries`, `inquiry_process_steps`, `inquiry_processors`, join table

The `inquiry` plugin implements a lightweight approval workflow entirely in
Elektra's local database — no OpenStack involvement.

**`inquiry_inquiries`:**
- `kind` — type of request (e.g. `"project"` for new project requests)
- `aasm_state` — AASM state machine: `new → open → reviewing → approved/rejected → closed`
- `payload` (JSON) — arbitrary request data (what is being requested)
- `callbacks` (JSON) — optional auto-run actions on state transition
- `tags` (JSON) — filterable labels
- `domain_id` / `project_id` — OpenStack scope where the request originates
- `approver_domain_id` — domain whose processors handle this inquiry

**`inquiry_processors`:** cached identity (uid, name, email) of users who can
process/approve inquiries. Populated from `service_user.identity` lookups.

**`inquiry_process_steps`:** audit trail — one row per state transition, recording
`from_state`, `to_state`, `event`, `processor_id`, and a description.

**State transitions** send email notifications via `InquiryMailer` (requester,
processors, additional recipients). All transitions go through
`Inquiry::Inquiry#proceed_state_change`.

**Plugin migration registration:** the `inquiry` plugin's migrations live in
`plugins/inquiry/db/migrate/`. They are added to Rails' migration paths by
`config/initializers/append_plugins_migrations.rb`:

```ruby
Core::PluginsManager.available_plugins.each do |plugin|
  ActiveRecord::Tasks::DatabaseTasks.migrations_paths.push(
    plugin.path + "/db/migrate"
  )
end
```

`inquiry` is currently the **only plugin** with its own migrations.

## ActiveRecord vs. ServiceLayer::Model — the key distinction

All plugin models in `plugins/*/app/models/` fall into one of two categories:

**DB-backed ActiveRecord models (only 4 + inquiry cluster):**
- `FriendlyIdEntry`, `ObjectCache`, `UserProfile`, `DomainProfile`, `ProjectProfile`
  — inherit from `ApplicationRecord < ActiveRecord::Base`
- `Inquiry::Inquiry`, `Inquiry::Processor`, `Inquiry::ProcessStep`
  — inherit from `Inquiry::ApplicationRecord < ActiveRecord::Base`

**OpenStack-mapped ServiceLayer models (everything else):**
- `Compute::Server`, `Networking::Network`, `Lbaas2::Loadbalancer`, etc.
- Inherit from `Core::ServiceLayer::Model`
- **No database backing** — they are wrappers around OpenStack API responses
- `save`/`update`/`destroy` delegate to service methods which call Elektron

The `application_record.rb` stubs in several plugins (cloudops, keppel, etc.) are
empty scaffolding with no tables — those plugins have no local data at all.

## Key files

- `db/schema.rb` — authoritative current schema (run `rails db:schema:load` for a fresh setup)
- `db/migrate/` — root migrations (friendly_id_entries, object_cache, profiles)
- `plugins/inquiry/db/migrate/` — inquiry-specific migrations (oldest: 2015)
- `config/initializers/append_plugins_migrations.rb` — adds plugin migration paths to Rails
- `config/database.yml` — PostgreSQL connection config (all env-var driven)
- `app/models/friendly_id_entry.rb` — slug mapping, `find_or_create_entry`, `search`
- `app/models/object_cache.rb` — API response cache, `cache_objects`, `find_objects`, `search_label`
- `app/models/user_profile.rb` — user display data, `find_by_name_or_create_or_update`, ToU check
- `app/models/project_profile.rb` — wizard state machine per project
- `plugins/inquiry/app/models/inquiry/inquiry.rb` — AASM workflow model
- `lib/core/elektron_middlewares/object_cache.rb` — middleware that populates `object_cache` table
- `app/services/dashboard/rescoping_service.rb` — populates `friendly_id_entries`
